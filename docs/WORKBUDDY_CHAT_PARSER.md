# WorkBuddy transcript 解析与当前输入契约 V1

## 格式依据与虚构回归样本

Step 5G 只直接读取用户提供的三份 `聊天记录.txt`，分别包含 3、4、5 条消息。三份文本都是 UTF-8，使用 LF，末尾有一个换行。

观察到的结构：

```text
发送人
2001年1月16日 09:47
正文

下一位发送人
2001年1月16日 11:24
下一条正文
```

- 第一行是发送人，第二行是完整日期及两位时、分。
- 后续消息头位于空行之后；发送人紧接日期时间行。
- Step 5G 的三份真实样本正文均只有一行。Step 5G.2 另外验收用户直接提供的七条完整 inline transcript，其中包含真实多行通知、emoji、正文日期及值班时间；文件与动画占位仍按各自已有证据判断，不扩大本轮结论。
- 原文姓名前的 `·` 保留。历史 Agent 快照省略该字符，属于历史加工差异，不能作为解析器的清洗规则。

## 输入与输出

`parseWorkBuddyChatHistoryText(text, { expectedMessageCount })` 是纯文本函数，不读取文件系统、目录名、文件时间或当前时间。

`expectedMessageCount` 来自当前卡片的明确消息数，仅用于验证消息边界；不用于推算时间或补足消息。当前导入契约最多接收 500 条。缺少计数、计数不合法或与解析结果不一致时，整份文本停止。

成功返回 `messages`、文法版本及独立的时区解释元数据。消息包含 `platform`、`sender_name`、`sender_name_source`、`content`、`content_source`、`timestamp`、`timestamp_source`、`source_position` 和原文时间行 `source_time_text`。

- 姓名和正文不做显示归一化，不删除符号，不逐行 trim。
- 只将 CRLF 统一为 LF、移除文件开头 BOM 和文件末尾一个行终止符。
- 相邻消息之间只消耗一个空行作为结构分隔，其他正文空行保留。
- 时间行只接受 `YYYY年M月D日 HH:mm`，并严格校验公历日期及时间范围。
- `timestamp_source = source_native` 指原文日期时分；`+08:00` 是系统解释，秒 `00` 用于表达分钟精度，不表示源文本提供了秒或时区。
- 没有可靠时间或不支持的时间格式时返回带行号的解析错误，不生成未知时间消息，也不补造时间。
- `source_position` 始终为文件原始顺序 `0,1,2,...`；解析器不排序、不去重。

## 停止策略与已知边界

解析错误抛出 `WorkBuddyChatParseError`，不返回已解析的部分数组。缺失发送人、时间、正文，非法日期，明显缺少消息分隔，以及计数不一致均停止。

正文中的普通日期句子保留。空行后的两行如果完整匹配消息头，V1 会将其识别为消息边界，再校验来源声明的消息数。正文中模拟消息头导致计数不一致时，明确拒绝，不猜测合并方式。

当前文本没有已确认的消息头转义或消息长度字段。正文模拟完整消息头，同时另一条消息头损坏等导致总数恰好抵消的情况，仅凭文本与总数无法排除。无前导标记的损坏消息头也可能与普通正文不可区分。此类来源格式需要额外证据，不能宣称任意文本都可安全恢复。

## 本轮接入范围

新增解析器和隔离测试，不修改通用 TXT adapter、Batch Tool API、Evidence schema、真实 Skill 或 Connector。批量集成测试使用明确标注的合成 ZIP fixture 满足当前证据门禁，不能作为目录证据已接入的证明。

alpha.15 发布前仍需吸收 alpha.14.1 维护修复，本轮不 cherry-pick。

## Step 5G.2 虚构 inline 回归样本

完全人工虚构的七消息 inline 回归样本，仅保留消息数量、重复关系、特殊空白、emoji 与时间结构。

- 隐私清理后不保留真实来源附件标识。
- 卡片显示文件名：`虚构聊天记录_20010117_120000.zip`；声明消息数为 7。
- fixture 保留来源 CRLF，无末尾行终止符；UTF-8 字节数 3,169。
- SHA-256：`7829f24d8504517c201830f935072f49a70dad8e44249b20ee028b48f820779e`。
- `.gitattributes` 仅禁止本目录 TXT fixture 的自动换行转换，保留现有字节哈希契约，虚构样本的换行契约保持固定。
- 七条虚构 inline fixture 单独声明 `cr-at-eol`，使 Git 接受原文 CRLF 的回车符，保留其他常规空白检查，不修改全局配置。
- 真实虚构说明82通知中的 `14：00-18：00` 使用全角冒号，不改写成半角。末尾 `2001年1月17日` 是正文落款，不是第八条消息。

当前消息来源方向为逐卡片绑定的完整 inline transcript；明确目录作为未来目录证据入口。TXT 用于原始证据、一致性检查及诊断，不自动覆盖或补齐 transcript。

## 当前输入附件实例门禁

`normalizeWorkBuddyCurrentInput(blocks)` 接收已提取、按 XML 规则解码一次的当前 transcript 元素字段。它是纯函数，不负责从任意文本搜索 XML，不读取目录，不验证目录实际存在，不缓存跨输入身份。

- 仅本次调用使用精确的 `extracted_dir_path` 字符串作为归组键，不改写路径、不解析别名、不按正文或 SHA 归组。
- 不同路径始终保留为不同实例，即使文件名、正文、消息数及内容哈希相同。
- 同路径必须具有相同文件名、声明消息数、首位发送人、首条时间及截断状态。省略截断标记与 `false` 都表示未截断；`true` 不允许作为完整来源。
- 每个副本分别经过现有 Parser。可用的首条元数据必须与解析出的首条消息一致。
- 比较既检查窄归一化后的来源文本，也检查完整解析结果，不仅比较消息数或正文哈希。
- 同路径元数据、正文、时间、发送人、顺序冲突，或副本不能完整解析时，抛出 `DUPLICATE_CONTEXT_CONFLICT`，整次输入不返回部分成功附件。
- 输出保留首次出现的原始 transcript 和全部 `context_indexes`。只有已经证明一致的副本才折叠，冲突时不选择任何一份。

允许的外层差异只有：开头 BOM、CRLF/LF、首个发送人前的纯换行、文档末尾最多一个行终止符。其余末尾空行、正文缩进、同行空格、Unicode、emoji、发送人及段落空行均保留；不使用 `trim()` 清洗 transcript 或正文。

最初输入契约隔离验收时，`gateWorkBuddyBatchCurrentInput(blocks)` 先调用归一化，再要求恰好两个逻辑附件。四份原始上下文可以对应两个独立附件；同一附件的两份副本仍只有一个逻辑附件，当时不能通过批量门禁。

上述早期验收只实现输入契约。既有 Batch Tool、正式 Skill、Connector 与目录证据当时均未接线或修改；当时批量接口仍要求真实 ZIP 路径，不把解压目录当作 ZIP 路径。

alpha.18 当前门禁仍先复用同一归一化与解析逻辑，再限定为一个或两个逻辑附件；同一附件的一致副本可以归为一个附件，零个或三个以上附件均拒绝。单卡、双卡都调用 `privateradar_ingest_current_context_batch`，原样提交本次真实原始上下文与明确目录；旧 `privateradar_ingest_messages` 只返回 `RAW_CURRENT_CONTEXT_REQUIRED`，不得降级调用。解析器的消息边界、来源事实及完整日期要求不变。
